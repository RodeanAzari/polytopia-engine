# 2026-11-08-sim-speed.png: simulator speed vs. Tribes' forward model

**Result:** on uniform-random playouts of the same levels, our C++ simulator makes **5.3–6.3× more decisions per
second** than Tribes' Java forward model (median of 3 runs per config; per-run range 4.4–7.2×), single thread each.

## Provenance
- **Code:** git `c2507a2` (`make bench N=200`, then `make plots`). Runs 1 and 3 report `-dirty`: the only
  uncommitted changes were `Makefile` (`plots` target) and `tools/plot_bench.py`, neither of which is timed.
- **Runs:** `data/results/bench-20261108-1112`, `-1115`, `-1118` (`.csv` per game, `.md` summary; gitignored).
- **Games:** 200 timed games per side and config, level seeds `10000·players` (+5000 for Score) onward;
  50 untimed Java warm-up games per config (rates were flat from 50 to 1,000 warm-up games).
- **Hardware:** Intel i9-11950H (16 threads), WSL2 on Linux 6.18; g++ -O3 Release; OpenJDK 17.0.20.1.

## Method
- Both sides run the turn loop of rule facts 04 §2 on the **true state, full observability**: at each decision,
  a uniform pick from the legal actions (End turn included); action generation after every executed action;
  no state copies (Tribes' `Game` copies the state for each agent call; search copies are a separate cost:
  ours is ~1.1 µs, ADR-005). Level generation and loading are not timed.
- Same levels, different random streams: Tribes' `java.util.Random` vs. our xoshiro, so the games differ
  move by move. Decisions per game agree within 3% in every config, so the two sides do the same amount of work.
- *decisions/s* = agent decisions (End turn included) per second of loop time; *playouts/s* = whole games
  per second.

## Interpretation and caveats
- The speedup is fairly stable (about 5–6×), but absolute rates moved by up to ±50% between runs of the same
  games on this WSL2 laptop (turbo and scheduling; no pinning). Quote the ratio and the ranges, not one run.
- No profiling or optimisation has been done yet: this is the baseline. Per-decision cost grows with game size
  (more units → more actions to generate), on both sides.
- Partial observability (fog) isn't benchmarked here.
